# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Stack

WordPress/Bedrock project using the Roots Sage theme framework.

- **Backend:** PHP 8.4, WordPress 6.8+, Bedrock boilerplate, Acorn (Laravel IoC container for WP)
- **Frontend:** Vue 3, TypeScript, SCSS, Bud.js (Webpack-based build), Bootstrap 5
- **Local dev:** Docker Compose (Nginx + PHP-FPM + MariaDB + Mailhog)
- **PHP style:** WordPress Coding Standards (Yoda comparisons, `array()` syntax)
- **PHP linting:** Laravel Pint with "per" preset (`pint.json`)
- **JS linting:** ESLint with Airbnb base + Vue 3 rules, 180-char line limit

## Commands

```

└── functions.php           # Theme entry point
```

### Key architectural patterns

- **Acorn services:** PHP business logic lives in `app/` as Acorn (Laravel-style) service providers, view composers, and components. Register services in `app/Providers/`, inject dependencies via the container.
- **Vue 3 components:** Interactive UI built as Vue 3 SFCs in `resources/scripts/Components/`. Components are mounted via `app.ts` or widget-specific entry points.
- **Blade + Vue boundary:** Static structure uses Blade templates; dynamic/interactive parts use Vue components embedded inside templates.
- **Data pipeline:** `resources/scripts/build.ts` generates static data files into `resources/data/` as a pre-build step (`npm run pre-build`), used by mapping/visualization features.
- **No jQuery:** ESLint is configured to forbid jQuery patterns (`window.jQuery`, `jQuery(`, `$(`).

### Environment

Local dev URL: `https://omakeikka.local.dev`. Configure in `.env` (`WP_HOME`). Copy `.env.example` to `.env` before first run. The domain must be in `/etc/hosts` pointing to `127.0.0.1`.

Nginx listens on port 80 (redirects to HTTPS) and 443. The dev server proxy in `bud.config.ts` proxies `http://omakeikka.fi` (production) and runs the HMR server on `http://localhost:3030`.

### Troubleshooting

**Blank white page (empty 200 response):** The active theme slug in the database may not match the theme directory name. Check and fix with:

```bash
docker compose run --rm wpcli option get template --path=/var/www/html/web/wp
docker compose run --rm wpcli option get stylesheet --path=/var/www/html/web/wp
# If they don't match the directory name under web/app/themes/:
docker compose run --rm wpcli option update template omakeikka-theme --path=/var/www/html/web/wp
docker compose run --rm wpcli option update stylesheet omakeikka-theme --path=/var/www/html/web/wp
```

**Bud public path for Bedrock:** Must use `/app/themes/<theme-slug>/public/` (not `/wp-content/...`), since Bedrock maps `wp-content` to `app`.

## Occupation CPT

The `occupation` CPT and `municipality` taxonomy are registered in `web/app/mu-plugins/occupation-cpt.php` (whitelisted in `.gitignore`). Both use the rewrite slug `ammatit`.

### URL structure

- `/ammatit/` - CPT archive (hub page)
- `/ammatit/putkiasentajat/` - single occupation post
- `/ammatit/espoo/` - municipality taxonomy archive

### Known rewrite rule conflict

WordPress auto-generates the CPT rule `ammatit/([^/]+)` before the taxonomy rule, so municipality archive URLs (`/ammatit/espoo/`) 404 without an explicit fix. The fix is `add_rewrite_rule()` with `'top'` priority for municipality slugs, registered on the `init` hook at priority 11 (after the CPT registration at 10). Flush rewrite rules after any change.

### Rank Math and JSON-LD

Do **not** output `schema.org` structured data via a `<script type="application/ld+json">` tag in Blade templates - Rank Math strips body-level JSON-LD. Inject custom schemas via the `rank_math/json_ld` filter from a PHP hook instead.

### Finnish grammar in occupation content

Occupation post titles are stored in plural nominative form (e.g. "Lähihoitajat"). CTAs and headings require other grammatical cases that cannot be derived programmatically. Store them as post meta:
- `cta_singular` - singular nominative ("lähihoitaja") for "Aloita X-haku" CTA
- `cta_partitive_singular` - partitive singular ("lähihoitajaa") for "Tarvitsetko X?" hero H1
- `cta_partitive` - plural partitive ("lähihoitajia") for "Etsitkö X?" CTAs and municipality section text
- `alt_titles` - JSON array of alternative plural titles (e.g. `["Hoiva-avustajat"]`) shown in hero as "Myös: ..."
- `municipality_locative` - inessive case per city ("Helsingissä") for term meta (future use)

The hero H1 uses `cta_partitive_singular` ("Tarvitsetko lähihoitajaa?"), not the nominative form. Using the nominative ("Tarvitsetko lähihoitaja?") or plural ("Tarvitsetko lähihoitajat?") is grammatically wrong.

### omakeikka app API integration

This WP site connects to the omakeikka Laravel app at `https://app.omakeikka.fi` via its public API. No authentication is required for these endpoints.

**Endpoints used:**
- `GET /api/occupations/{isco_code}/municipalities` - returns municipalities where employees with the given ISCO occupation code are registered. Used by `SingleOccupation` view composer to populate the city section on occupation pages. Results cached in WP transients (`occupation_municipalities_{isco_code}`) for 1 hour.

**Companion repo:** `~/repos/omakeikka` (Laravel app). The API endpoint above is defined in `routes/api.php` and handled by `App\Http\Controllers\OccupationMunicipalityController`. The service class is `App\Services\OccupationMunicipalitiesService`.

**Adding new API calls:** Use `wp_remote_get()` with `'timeout' => 5` and an `Accept: application/json` header. Always cache results with `set_transient()`. Return an empty array on any error - the template sections use `@if(!empty(...))` guards.

### Occupation content structure

Single occupation pages (`single-occupation.blade.php`) show content in this order:
1. **"X omakeikassa"** h2 - describes the talent pool available in omakeikka (first, most relevant to employers)
2. **"Mitä X tekevät?"** h2 - explains what the occupation involves

The "X omakeikassa" text must be based on actual profile data from the occupations JSON. Do not mention specific organisations by name - describe industries and role types only.

### SVG icons

Icons for all 15 occupation groups live in `resources/images/occupations/{isco_code}.svg`. Named by ISCO code (e.g. `5321.svg`). Bud.js copies them to `public/images/occupations/` via `.assets(['images'])` in `bud.config.ts`. All icons use `currentColor` for easy theming.

### Seed script

Data for local dev: `scripts/seed-occupations.php`. Run with:

```bash
docker compose run --rm wpcli --allow-root eval-file scripts/seed-occupations.php
```

**Wipes all occupation posts** on each run, then recreates the top 15 occupations by registered employee count sourced from `prompts/occupations_28032026.json`. Municipality taxonomy terms are created idempotently (looked up by `municipality_id` term meta). Municipality assignments for occupations that have real data are hardcoded from the production API; new occupations use empty arrays (display still works via the runtime API call in `SingleOccupation.php`). After seeding, flush rewrite rules.

### DB export

The `wpcli` container runs as a non-root user and cannot write directly to the bind-mounted host directory. Export to stdout instead:

```bash
npm run wp:db:export    # saves to backups/YYYY-MM-DD-HHMMSS.sql
```

The `mariadb-dump` binary inside the container also needs `--skip-ssl` (same as `mariadb`). The wrapper lives at `.docker/wpcli/mariadb-dump` and is mounted into the container via `docker-compose.yml`.

## help_request CPT and the household help request form

Households cannot post tasks in the omakeikka app: `marketplace_requests.poster_employee_profile_id`
is a non-nullable FK to `employee_profiles` and the routes sit behind an `employee` middleware. The
public form on this site is the buyer entry point, and it stores to WordPress, not to the app.

### Where things live

- `web/app/mu-plugins/help-request-cpt.php` — the CPT, meta, admin columns, status, retention cron
  and the GDPR export/erase hooks. **Whitelisted in `.gitignore`**; a new mu-plugin that is not
  listed there will never be committed.
- `app/Services/HelpRequestForm.php` — validate, store, notify. Posts to `admin-post.php`.
- `app/Services/Municipalities.php` — reads `resources/data/municipalities_full.json`.
- `app/Services/HouseholdDeduction.php` — kotitalousvähennys eligibility per group and category.
- `app/View/Composers/HelpRequestPage.php`, `resources/views/template-help-request.blade.php`,
  `resources/views/partials/{help-request-form,who-can-buy,deduction-notice}.blade.php`.

### register_post_meta is a deliberate new pattern

This is the only place in the repo that uses `register_post_meta()`. The older CPTs rely on
`supports => custom-fields` plus bare `update_post_meta()`, which puts sanitisation at whichever
call site remembers it. That is not acceptable for personal data, so every `_hr_*` key declares a
`sanitize_callback` that runs on every write path, plus an `auth_callback`. Keys are underscore
prefixed, which makes them protected meta: invisible to the Custom Fields UI and not settable via
`$_POST['meta_input']`.

`show_in_rest` is `false` on both the post type and every meta key. The other two CPTs use `true`;
here it would expose submitter names, emails and phone numbers on `/wp-json/wp/v2/help_request`.

### The Vue in-DOM compiler, and why the form needs v-pre

`index.php` wraps every Blade template in `<div id="app">`, and `bud.config.ts` sets
`app.vue.set('runtimeOnly', false)` while `app.ts` calls `createApp({}).mount('#app')` with no
render function. Vue therefore compiles the whole rendered page as an in-DOM template on every page
load. Any `{{ }}` in first-party text is a Vue expression.

The help request form is the first place user-submitted text is echoed back into Blade, so it is the
first place this matters. **`v-pre` on the form wrapper is required**, otherwise a visitor who types
`{{7*7}}` into the description sees `49` when the form re-renders with their values.

### No rewrite flush is needed

The CPT is registered with `rewrite => false`, `public => false` and `query_var => false`, so it
generates no rewrite rules. The form target is an ordinary WP Page. `deploy.php` never runs
`wp rewrite flush`, so a design that needed one would be a deploy hazard.

### Required manual steps

1. **Create the form page** and assign the template. It is not created by code:
   ```bash
   wp post create --post_type=page --post_status=publish \
     --post_title='Julkaise avunpyyntö' --post_name=julkaise-avunpyynto --porcelain
   wp post meta update <ID> _wp_page_template template-help-request.blade.php
   ```
   `MarketplaceCategoryQuery::helpRequestPageUrl()` finds it by that template meta and falls back to
   the app URL until it exists.
2. **Exclude the form page from LiteSpeed full-page caching** (Cache, Excludes). Otherwise the nonce
   and the `?virhe=` error render get served to the wrong visitor. The nonce soft-fails as a safety
   net, but the exclusion is the actual fix.
3. **Set `HELP_REQUEST_EMAIL`** in `.env`, comma separated for more than one recipient. Falls back to
   the admin email.
4. **Configure wp-mail-smtp** against the real sending domain with SPF and DKIM on `omakeikka.fi`.
   Until then `wp_mail` falls back to PHP `mail()` and lands in spam or vanishes. This is a launch
   blocker, not a nice to have. Locally the PHP image has no sendmail, so use the installed
   WP Mail Catcher or point wp-mail-smtp at `mailhog:1025`.
5. **Add the "who can buy" section to the homepage** with Elementor's Shortcode widget:
   `[omakeikka-kuka-voi-ostaa]`. The homepage is Elementor content, so Blade cannot include it there.
6. **Update `/tietosuojaseloste/`** with the data categories, purpose, legal basis, recipients and
   the retention schedule below, and re-run the Complianz privacy statement wizard.

### Retention

A daily `omakeikka_help_request_cleanup` cron, batched at 100 posts, with the schedule in the three
`OMAKEIKKA_HELP_REQUEST_*_DAYS` constants: IP hash dropped at 30 days, name, email and phone dropped
and the description anonymised at 12 months, whole record deleted at 24 months. Anonymise runs before
delete so the funnel counts survive the personal data purge. Raw IPs are never stored, only
`wp_hash()` of them.

### Kotitalousvähennys copy

`HouseholdDeduction` carries **no percentages, caps or euro amounts** by design. The rate depends on
the tax year and on how the individual helper invoices, and the 2026 increase (HE 113/2026 vp) was
still unratified when this was written. The site says the deduction may be available and links to
vero.fi, which is true in any year.

Eligibility is still gated, because saying the deduction may apply to excluded work is itself a
false claim. `muutto` is excluded by name in vero.fi guidance, `kauppa` only qualifies as part of a
larger service, `etaapu` fails the "work done in the dwelling" test, and `auto` is not work on the
dwelling. Status `no` renders nothing at all rather than a negative claim.

The mapping fails closed (`?? 'no'`), so a thirteenth group added to
`scripts/seed-marketplace-categories.php` never silently inherits a tax claim. `HouseholdDeduction::UPDATED`
drives both the visible date stamp and an `admin_notices` warning once it is over a year old.
